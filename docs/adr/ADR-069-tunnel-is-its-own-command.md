# ADR-069 — The bastion gets its own verb: `tunnel` leaves `port-forward`

- **Status**: Accepted
- **Date**: 2026-08-09
- **Revises**: [ADR-045](ADR-045-external-endpoint-port-forwards.md) in its CLI surface only —
  the ADR that created the bastion left the client work "outside this ADR" (§Rollout), and the
  implementation reached for the verb that already existed. Nothing it decided about the
  resource, the mint, the grant ceremony, the permissions or the wire is touched here
- **Revises**: [ADR-032](ADR-032-tcp-tunnel-cli-websocket.md) in what `port-forward` accepts as
  a target: containers AkerDock deploys, and nothing else — which is what ADR-032 itself said
  before ADR-045 borrowed the verb
- **Extends**: [ADR-060](ADR-060-dev-ingress-tunnels.md) §3, which rejected `tunnel` as the
  ingress verb *because the word already means the egress bastion*. That reasoning is upheld
  and completed: the word is now spoken where it was already understood
- **Related**: [ADR-033](ADR-033-cli-cobra-migration-run-modes.md) (the command tree),
  [ADR-064](ADR-064-one-transport-ladder-for-every-cli-tunnel.md) (one transport under both
  doors — this ADR moves a door, never a rung),
  [ADR-068](ADR-068-ending-a-live-session.md) (who may end a session; `tunnel close` is a
  client for the endpoint it decides, not a second authorization model)
- **Related PRD sections**: §5.7, §12, §23.3, §26

## Context

`akerdock port-forward` carries two products under one verb.

One is ADR-032's: a TCP tunnel to a container the platform deploys, named by a REF, with a
remote port the caller chooses — `port-forward db/pg 15432:5432`. The other is ADR-045's
bastion: a tunnel to a target the platform does *not* run, declared in advance by an admin
with its host and port frozen, reached through a grant ceremony — `port-forward
endpoint/prod-replica`. They share a transport (ADR-064) and a session table. They share
nothing else, and the seams show in the code that had to hold both:

- **The arguments stopped being positional.** `splitForwardArgs` tells a REF from a ports
  argument *by shape* — "a REF always contains a slash and a ports argument never does" —
  because `port-forward endpoint/x` has one argument where `port-forward 15432:5432` also has
  one. The comment on that function records the bug it was written to fix.
- **The remote port became a fiction.** For an endpoint there is nothing remote to name, so
  the argument survives only to give the local port a place to be written, and the code carries
  `localPort, remotePort = 0, 0` plus a `target = "the endpoint's declared target"` branch in
  the line announced to the developer.
- **The mint body is chosen by sniffing the mint path.**
  `if !strings.HasPrefix(mintPath, "/external-endpoints/")` decides whether the request has a
  body at all. Two protocols, one function, disambiguated by string prefix.
- **The help text cannot be written.** The current `Short` is "Tunnel a local port to a
  container port, or to a declared external endpoint", and the examples list two commands whose
  arguments do not mean the same things.

The vocabulary was already settled everywhere else. The dashboard's navigation entry is
**Tunnels**; the API's own summary is "List the team's **tunnel** sessions"; ADR-060 §3 turned
down `tunnel` for the ingress verb on the express ground that the word "overloads … the egress
bastion's UI (ADR-045)". Every surface the user meets says *tunnel* except the one they type.

## Decision

### 1. `akerdock tunnel` is the bastion's command, and it is a group

```
akerdock tunnel open ENDPOINT [LOCAL_PORT]
akerdock tunnel ls [--endpoint NAME] [--all]
akerdock tunnel close SESSION_UUID
```

A group rather than a bare verb, because the bastion is the one tunnel family with an
operational life beyond opening one: sessions outlive the terminal that opened them, an admin
revokes them, a grant expires under them. `GET /port-forward-sessions` and
`DELETE /port-forward-sessions/{uuid}` have shipped since ADR-045 and had **no CLI client at
all** — a developer could open a tunnel from the terminal but had to reach for a browser to see
or close it. The group is what gives those endpoints their first caller; **no API surface is
added, changed or generated by this ADR**.

### 2. The endpoint is named bare, not as a REF

`tunnel open prod-replica`, not `tunnel open endpoint/prod-replica`. The `type/name` REF exists
to disambiguate a target among kinds a command accepts several of (`logs app/x` vs
`logs db/x`); `tunnel open` accepts exactly one kind, so the prefix carries no information —
it is the same reasoning that made `akerdock ingress dev-kedric 3000` take a bare name
(ADR-060 §3), and the two mirror commands now read alike. The positional argument that follows
is unambiguously a local port, so the shape-sniffing goes away with the ambiguity that
required it.

### 3. `port-forward` refuses `endpoint/…`, immediately and by name

No deprecation alias. The refusal is an error that names the replacement
(`use \`akerdock tunnel open <name>\``), which teaches the new command at the exact moment the
old one is typed — an alias that keeps working teaches nothing and leaves two spellings in the
help, the docs and the support answers. The CLI is pre-1.0, the affected surface is one verb
form used by one instance's developers, and the cost of being wrong is one line of terminal
output.

`port-forward` goes back to ADR-032's sentence: a TCP tunnel to a container AkerDock deploys.

### 4. `tunnel ls` shows every tunnel session, not only the bastion's

The listing is the team's whole tunnel table — application, database, service, preview and
external endpoint — with a `TARGET` column that names the kind. This is deliberate and it is
not a leak of `port-forward` into `tunnel`'s group: **ADR-045 already decided this exact
question** when it built the dashboard view, and decided it for a reason that has not changed —
"the operational question is *what is currently forwarded out of this team*, not *out of this
endpoint*". A `ls` that silently hid the container forwards would answer a question nobody
asks, and would do it invisibly.

`--endpoint NAME` narrows to one declared endpoint (the API's existing
`external_endpoint_uuid` filter); `--all` walks the history instead of the live sessions
(the API's existing `active=false`). The command group is named after the session family it
lists; `open` is the one verb in it that is bastion-specific, and that is the smaller
irregularity.

### 5. Nothing below the command line moves

Same mint (`POST /external-endpoints/{uuid}/port-forwards`, empty body), same `akdp_` token,
same `akerdock-tunnel-v1` subprotocol, same ADR-064 ladder, same permissions
(`port-forwards:open`, `external-endpoints:manage`), same grant choreography with its
`access_request_required` polling, same `authorized_until` announcement. A wire identifier is
bound to an access path (ADR-027) and no access path is created here: this ADR renames a door,
not a corridor. In particular `tunnel close` is a client of the endpoint ADR-068 decides the
authorization of, and inherits whatever that ADR lands — it states no rule of its own.

`akerdock ingress` is untouched. Three commands, three products: `port-forward` outward to a
container, `tunnel` outward to a declared external target, `ingress` inward to the laptop.

## Consequences

- The `endpoints` REF kind (`endpoint/`, `ep/`) is no longer reachable from any command. It
  stays in `refKinds` unused — `tunnel open` resolves the endpoint by bare name through the
  same `/external-endpoints` listing — and a future command that must disambiguate an endpoint
  among kinds will find it there.
- `docs/specs/cli.md` §7.1 becomes its own section (§7 stays ADR-032's port-forward); the
  in-app documentation page (PRD §25.4) and the dashboard's copyable command snippets follow.
- One command's tests split in two: what covered the endpoint path in `portforward_flow_test.go`
  moves to the new command's, and the shape-sniffing test in `cli_test.go` loses its subject —
  `splitForwardArgs` keeps only the "REF or ports, one argument" case that ADR-032 always had.

## Alternatives rejected

- **`tunnel` as the umbrella of both** (`tunnel port-forward` / `tunnel endpoint`): rejected.
  It makes the common command longer to serve a taxonomy the developer does not need at the
  moment they type it, and it would have to swallow `ingress` too to be honest — ADR-060 chose
  a one-word verb for exactly that feature and this ADR does not reopen it.
- **`bastion` as the verb**: rejected. It is the accurate word for the *architecture* and the
  wrong word for the *act*; the UI, the API summaries and ADR-060's naming section all already
  say "tunnel", and inventing a fourth word for the thing three surfaces agree on is the
  opposite of the vocabulary work this ADR is doing.
- **Keeping `port-forward endpoint/…` as a deprecated alias**: rejected — see §3.
- **Leaving it alone**: rejected. The seams listed in Context are not cosmetic; they are a
  positional-argument parser that reads by shape, a mint that picks its body by string prefix,
  and a pair of shipped endpoints with no client. Each of those is cheaper to fix once the two
  products stop sharing a verb.

## Verification

Unit tests, per the project's pyramid (ADR-026/028):

- `tunnel open <name>` resolves an endpoint by name, mints with an **empty body**, and opens the
  session — the ADR-045 path, moved.
- `tunnel open <name> 15432` binds the requested local port; with no port argument the OS picks
  one and it is announced.
- `tunnel open endpoint/<name>` fails with a message naming the bare form (the migration case,
  since that is what a hand or a script will type first).
- `access_request_required` still opens the grant page and replays the mint until it succeeds
  (choreography unchanged, now under the new verb).
- `port-forward endpoint/<name>` fails with a message naming `akerdock tunnel open`.
- `tunnel ls` renders every target kind; `--endpoint` sends `external_endpoint_uuid`, `--all`
  sends `active=false`; `-o json` emits the API objects unaltered.
- `tunnel close <uuid>` issues the `DELETE` and treats `204` as success.
