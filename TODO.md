## P1 — Usable PaaS

### 1. Managed databases (§6) — PostgreSQL done, engines and SSL remain
- [x] `databases` + `database_credentials` migration (envelope-encrypted passwords)
- [x] `POST /databases/postgresql`, `GET/PATCH/DELETE /databases/{uuid}` + `start`/`stop`/`restart` (8 operations)
- [x] Idempotent provisioning job (volume, network, generated credentials, wait for `pg_isready`)
- [x] Public port reservation: `(server, port)` uniqueness guaranteed in the database (§22.3)
- [x] INV-003 redaction: password and URLs only with `read:sensitive`
- [x] **External URL** (`external_url`): built only if the database is *actually* reachable from outside (`is_public` **and** port bound) — a published connection string that does not connect is worse than no string at all: it looks usable. Proven E2E by actually connecting to it
- [x] **Database SSL** (§6.3, amendment no. 23): **one CA per server** — the server is the blast radius; a leaked instance-wide CA would allow impersonating *all* databases on *all* servers. The CA private key never leaves the control plane (encrypted at rest); what goes to the server is a signed leaf, and what goes to the client is the **CA certificate — public by nature**, because it is what lets the client *verify*: TLS the client does not verify protects against nothing. Proven E2E with `sslmode=verify-ca`. The postgres uid is **read from the image**, not guessed (999 on Debian, 70 on Alpine): guessing it yields a database that starts, cannot read its own key, and restarts in a loop
- [x] **Dynamic TCP proxy** (§6.2, §2.6, amendment no. 22): in `tcp_proxy` mode, the database publishes **no** port on its container — the proxy does the listening. Changing the public port therefore recreates the **proxy** (a few seconds, no data touched) instead of restarting the database (and cutting every open connection). The entrypoint is static because Traefik cannot add a listener at runtime: that is precisely why the port lives there. `HostSNI(`*`)` = raw passthrough, the database's TLS goes through untouched. Byte-for-byte conformance fixture
- [ ] The 7 other engines (MySQL, MariaDB, MongoDB, Redis, KeyDB, Dragonfly, ClickHouse) — **out of v1 by product decision**: the contract records "PostgreSQL only". Adding them requires an amendment + an engine abstraction (provisioning, backup, drill): dedicated batch

### 2. Backups and restore (§7, §20.5, ADR-014) — done, except the drills
- [x] `s3_storages`, `database_backup_plans`, `backup_executions` migration
- [x] Backup plans (validated cron/aliases), executions, `restore` (202 + job) — 6 operations
- [x] Backup job: `pg_dump` inside the container, SHA-256 checksum, size, engine version
- [x] Restore with **mandatory integrity verification** — a corrupted dump is never restored
- [x] Local retention: the last valid backup is never deleted
- [x] **S3 upload**: home-grown S3 client (SigV4, `internal/s3` — no AWS SDK, cf. ADR-021), `/s3-storages` CRUD (5 operations, spec amendment no. 10), write/read/delete verification before declaring a bucket usable
- [x] The dump goes **from the server to the bucket directly** via a presigned URL passed to `curl` through stdin (never in argv, INV-003) — never transits through the instance; upload confirmed by the size read from the bucket
- [x] Upload failure ⇒ `partial` status (the local backup exists), never a silent success; `s3_only` only deletes the local copy after confirmation (INV-008)
- [x] Restore from the bucket (re-download then checksum verification, as for a local dump)
- [x] S3 credentials in the master key rotation inventory (ADR-003)
- [x] Local and S3 **retention**, independent and cumulative (count **and** age) — the last successful backup is never purged, whatever the rules
- [x] **Scheduled execution**: internal cron parser (`internal/cronexpr`, unit-tested — ranges, steps, time zones, DST), `next_run_at` owned by the scheduler, non-overlapping triggering (per-plan `lock_key`) — proven E2E without any manual call
- [x] **Automatic restore drills** (ADR-014, spec amendment no. 16): the latest dump is restored into a **throwaway** database on the same server — never into the live database, a drill touching production would be a scheduled outage — then the database is destroyed, including on failure (leaving it "for inspection" would leave a copy of production data on the server)
- [x] **The drill compares, it does not merely avoid failing**: the source database's table count is recorded **at dump time**, and the drill requires the same count on the way back. A dump can decompress cleanly, restore without error and contain nothing — a `psql` restoring emptiness exits 0 (`ON_ERROR_STOP=1` turns "a few errors printed" into "restore failed")
- [x] **A failing drill is loud**: `backup.drill_failed.v1` (critical by suffix) — this is exactly the failure mode the feature exists to catch: backups green for months that restore into nothing. A failed drill is a **result**, not a job to retry: the dump will not become restorable by trying again in a minute

### 4. Remaining build packs (§5.2) — static and nixpacks done
- [x] **Static** (Nginx): synthesized Dockerfile (no toolchain executed at build time), nginx config with SPA fallback to `index.html`, `publish_directory` validated (INV-012)
- [x] **Nixpacks**: binary pinned per release (`NixpacksVersion`), provisioned at onboarding (non-blocking failure) and reinstalled on demand at build time; plan traced in the logs; build variables via the environment, never in argv
- [x] **Railpack** (beta) — explicitly refused with `422` (`not_implemented`), never silently treated as Nixpacks
- [x] **Build args and BuildKit secrets** (§5.2, spec amendment no. 14): `build.env` was sourced but `docker build` **does not inherit the environment** — no build variable ever reached the Dockerfile. Worse, `is_secret` **was neither exposed by the contract nor persisted**: every build variable would have become a `--build-arg`, hence visible in `docker history`. From now on: ordinary variable → `--build-arg`; secret variable → **BuildKit secret** mounted for the duration of a `RUN`, absent from all layers (INV-003). Proven E2E: the secret is neither in the history, nor in the config, nor in a layer
- [x] **Nixpacks static mode**: the nixpacks image is only the *builder* — what ships to production is nginx serving the produced directory. Deploying the builder image would embed the whole toolchain **and would serve nothing**: the build command exits, and a container whose command exits is a downed container. Proven E2E: the site is served, and `node` is **absent** from the deployed image
- [x] **Dedicated build servers** (§3.4, spec amendment no. 19): a second machine builds, pushes to a registry, and the deployment server **pulls by digest** — the digest is what makes "the image that runs" and "the image that was built" provably identical, and it is what a rollback replays. Without a push registry, `use_build_server` is refused with `422`: the image would stay on the build machine and the target could never pull it. A build server routes nothing (no proxy) and cannot be a deployment target. **Random** selection among ready build servers (a fixed order would send everything to the same machine, which is the opposite of the goal); incompatible architectures refused before producing an `exec format error` that would look like an application bug
- [x] **Private registries** (amendment no. 17): password encrypted at rest, never read back by the API, reaching the server only through the **stdin** of `docker login --password-stdin` — never in `argv`, where a `ps` would read it; `docker logout` guaranteed after the pull, including on cancellation

### 5. Certificates (§4.3) — done, alerting and DNS-01 remain
- [x] `certificates` migration (observed reflection, §18.3 — no private key stored)
- [x] `GET /servers/{uuid}/certificates` (+ `expiring_within_days` filter), `GET /certificates/{uuid}`, `POST /certificates/{uuid}/renew` (202 + job)
- [x] `certificate.sync` job: reads the proxy's `acme.json` over SSH, parses the public chain (`x509`), reconciliation
- [x] `certificate.renew` job: backs up the ACME store then restarts the proxy — the old certificate keeps serving
- [x] **D-30/D-7 expiry alert**: the scheduler emits `certificate.expiring.v1` into the outbox — once per crossed threshold, never on every pass
- [x] **DNS-01 for wildcards** (proxy-contract §7.2, amendment no. 21): a wildcard **cannot** be validated over HTTP-01 (the CA has no unique host to query) — a `wildcard_domain` without a DNS-01 credential is therefore refused with `422`, instead of leaving every preview URL on the self-signed certificate, forever, with nothing saying so. The credential is **materialized as a 0600 `acme.env`** and injected via `--env-file`: never in `traefik.yaml` (which is checksummed, stored as a revision and read back — a secret in there would be a second copy of the secret in the database). Conformance fixture: a route under the wildcard goes through DNS-01, a route outside the wildcard stays on HTTP-01

### 6. Notifications (§11, ADR-019) — ADR upheld, channels remain
- [x] `notification_channels`, `notification_rules` (encrypted config) and `notification_deliveries` (idempotency + history) migrations
- [x] 7 `/notification-channels` operations (+ rules, + test send) — spec amendment no. 11
- [x] **Outbox consumption** by the scheduler with a cursor; a purge never goes past the cursor (an alert cannot be lost to retention)
- [x] **Routing** by project/environment/severity; anti-flapping **debounce** and **quiet hours** (window straddling midnight) — a `critical` event always crosses both
- [x] **Webhook, Slack, Discord** channels; suppressed sends are logged (`suppressed_reason`), never lost
- [x] **SMTP, Resend, Telegram, Pushover** channels (spec amendment no. 18): a channel is validated **for the transport it claims to be** — a `telegram` channel carrying a webhook URL and no `chat_id` would be accepted, stored, then fail at the only moment that matters. SMTP encryption is **declared, never inferred from the port**: inferring it means one day sending the password and the alert in cleartext with nothing saying so (and if the server offers no STARTTLS while a password is configured, the send is **refused**). The Resend key goes in a header, never in the URL (a URL travels through logs, proxies and referrers). Payload shape tested against a real server for every provider; SMTP proven **E2E against a real relay** (mailpit) — the assertion is that the mail *arrived*, not that the code did not crash
- [x] **Deferred digest**: `pending` deliveries *are* the queue (no table to synchronize); a `critical` never waits for a digest; window configurable per rule

### 7. Team invitations (§10.1) — done, email remains
- [x] `GET/POST /teams/{uuid}/invitations`, `DELETE .../{invitation_uuid}`
- [x] The link is a secret: only its SHA-256 is stored, the cleartext value is returned only once (§23.2)
- [x] **Delivery by transactional email** (§14.2, amendment no. 20): instance relay (SMTP or Resend) **verified before being accepted** — an unreachable relay is refused where the operator is looking, not at the first invitation where the only symptom would be a mail that never arrives. The email is an **addition**, never a replacement: the link stays in the response (§23.2), otherwise an instance without a relay could no longer invite anyone and a misconfigured relay would swallow the invitation

### 8. Per-resource scheduled tasks (§5.7)
- [x] `scheduled_tasks` / `task_executions` migrations + 7 operations (spec amendment no. 15): cron validated on input by the **same** `cronexpr` as the scheduler — an expression the scheduler will not know how to trigger is refused with `422`, never accepted then never launched
- [x] **Execution by the scheduler** (proven E2E **without any manual call**): `docker exec` in the resource's container, command **quoted** and not sanitized (it is intentional shell), output **truncated by the queue** (the tail is kept — that is where the error is) and capped at 64 KiB
- [x] **An occurrence that did not run leaves a trace** (`skipped` + reason): an empty history reads exactly like "nothing was ever scheduled" — that is how a nightly job disappears for a month
- [x] `overlap` policy (`skip` by default: a cron firing faster than it finishes does not pile up executions) — applied **to manual triggering as well**, otherwise the policy would have a backdoor
- [x] `missed_run` policy (`run` / `skip`): "missed" is defined by the **cron's own period** (a minutely task tolerates a minute of lateness, a daily task a day) — no magic constant
- [x] A failing command is a **result**, not a job to retry: the exit code is recorded in the history and `scheduled_task.failed.v1` goes into the outbox (critical by suffix, ADR-019). Retrying would have re-run the operator's command behind their back

## Technical debt and hardening

### Security
- [x] **SSH host key pinning** (§20.1): trust-on-first-use, fingerprint pinned at onboarding and compared in constant time on every connection. The `sshexec.Dial` parameter is **mandatory** (the compiler forces every caller to decide); a changed key raises `ErrHostKeyChanged`, is **never** re-pinned automatically, and the failure says so explicitly
- [x] **Explicit ACME contact email** (`AKERDOCK_ACME_EMAIL` → `instance_settings.acme_email`, database authoritative afterwards). It used to be **guessed** (`admin@example.com` as a last resort — an address Let's Encrypt refuses): the proxy started, everything looked healthy, and the certificates never arrived. Without an address, server onboarding **now fails immediately**, where the operator is looking. Added to the reference compose and to `.env.example`
- [x] **Browser sessions** (§698, outside the v1 contract scope — `/auth/*` lives next to `/api/v1`, like the webhooks): **HttpOnly** session cookie (the page cannot read the secret it authenticates with — an XSS no longer walks away with an API token) + **double-submit CSRF** (a cookie is sent on requests that *another* site triggers: it proves which browser is calling, never that the user meant to call; Bearer calls are exempt — there is no ambient credential to forge). **Constant-time** login (the dummy hash is a real Argon2id: without it, an unknown email answers faster and accounts become enumerable) and identical message for an unknown email and a wrong password. Logout **revokes server-side**; account lockout bounds online *brute force*. Bug found along the way: bootstrap created a root user **without a team** — an account that could authenticate and then be told it belongs nowhere
- [x] **WebAuthn passkeys** (hardening of §698): *usernameless* enrollment and login (`/auth/passkeys/*`, `/auth/passkey/login/*`, outside the v1 contract like the rest of `/auth`). The relying party is **pinned to the instance FQDN**, never derived from the Host header — a derived RP would let anyone who can make the server answer under another name mint credentials for it (`localhost` fallback in dev only, the only origin browsers treat as secure over HTTP). `ResidentKey` **and** `UserVerification` required: a passkey replaces the password, not merely presence. Single-use ceremonies (`DELETE … RETURNING`, only the token hash in the database, 5 min TTL) proven against a real PostgreSQL; signature counter persisted **before** the session opens, and a counter going backwards (clone) refuses the login, loudly. Crypto verification is delegated to `go-webauthn` — hand-rolled CBOR parsing would be exactly the opposite of the goal
- [x] **Security headers on the whole port** (`httpserver.SecurityHeaders`): CSP (`script-src 'self'`, `frame-ancestors 'none'`, inline styles tolerated — Angular injects component styles that way; inline *scripts* remain forbidden, that is where the value is concentrated), nosniff, Referrer-Policy, COOP/CORP; HSTS **only** with an FQDN — promising it on an HTTP instance would lock the operator out for the duration of the max-age. UI rendering verified under this CSP in a real headless Chrome
- [x] **Per-IP rate limit on `/auth`** (30/min): `Login`'s comment promised a limiter that did not exist — `/auth/login` and the passkey endpoints are the only ones that turn a guess into a response without a credential. Key = `RemoteAddr`, never `X-Forwarded-For` (a key the client writes is bypassed by rotating a string); an unparsable address shares a bucket instead of being exempted. The terminal WebSocket sits behind the same limiter: it too answers without a Bearer credential
- [x] **Passkey step-up** (rbac-matrix §5): dedicated WebAuthn ceremony (`/auth/passkey/stepup/*`), **purpose distinct** from the login one — a login ceremony cannot be redeemed as a step-up. The asserted credential must belong to the session's user: a valid passkey belonging to someone else elevates nothing. Consumed by the server terminal; the other sensitive actions in the grid (restore onto a non-empty database, CA rotation) will be able to hook into it
- [x] **TOTP MFA** (§10.2, §23.3; `/auth/mfa/*`, outside the v1 contract like the rest of `/auth`): RFC 6238 implemented in-house (`internal/totp`, pinned to the RFC 4226/6238 vectors — the algorithm is an HMAC, a truncation and a modulo; a dependency would be more code to audit). **Two-step** login: the password buys a 5 min *challenge* (`mfa_challenges` table, hash only in the database, consumed via `DELETE … RETURNING` — same construction as the passkey ceremonies), never a session; secret envelope-encrypted (AAD bound to the row uuid), **per-step replay protection** persisted in SQL (`last_used_at`, two concurrent verifications of the same code do not win twice); 10 single-use recovery codes (SHA-256 — 64 random bits, nothing a GPU can shorten), shown a single time; a wrong code counts toward the **account lockout**, not just the IP rate limit. **Disabling requires a valid code** (a hijacked session does not unplug the second factor in one click) and is **audited**. An unconfirmed factor keeps nothing: enrollment is only active after a first valid code. Passkey logins **skip** the TOTP (a passkey is already a second factor, phishing-resistant on top) and `mfa_verified_at` stays reserved for the passkey step-up — rbac-matrix §5 requires *that* ritual for the root terminal, a TOTP typed at login must not bleed into it
- [ ] Validation of `custom_docker_options` (INV-012) when the field gets exposed

### Deployment engine
- [x] **State-based crash recovery** (§2.5/§4): up to `healthchecking`, replay (every remote effect is idempotent or destroyed-then-redone). During `switching`, **remote inspection first** — what exists on the server decides: candidate already promoted ⇒ finish; old one gone ⇒ resume at the rename; both alive ⇒ resume at stopping the old one; nothing usable ⇒ **loud** failure, never a second blind switchover (INV-004/005)
- [x] **Crash ≠ failure** (bug found by this test): `max_attempts=1` made terminal *every* deployment whose worker died. The reaper **gives the attempt back** (the job survives the crash, INV-013), bounded by `resume_count` so that a *poison pill* still ends up in the dead-letter
- [x] **Compensation repaired** (bug found by this test): `execute()` closed the SSH connection before the compensation attempted its `docker rm` of the candidate — it had **never** cleaned anything up until now
- [x] Expiry alert: a certificate at D-5 crosses D-30 **and** D-7 — it is announced **a single time**, at the nearest threshold
- [x] **Multiline values** (PEM keys, JSON blobs): values are sourced from a shell file (single-quoted literals) and passed to Docker **by name** (`-e KEY`) — they arrive intact and stay out of `argv` (INV-003). The quoting is tested against a real shell, not eyeballed

- [x] **Remote `remnants` + `acknowledge_remnants`** (§20.6.4): the code announced "remnants recorded" and **recorded nothing**. ## Test pyramid

The historical seven-stack DinD suite was removed (ADR-028). The only remaining
E2E verifies the complete seam SSH → Docker → Traefik, including a rolling
switchover under traffic. It runs after merge and before release, not on
pull requests.

Validations, remote commands, states, RBAC, webhooks, queue, proxy,
notifications and UI behaviors belong to the unit/module tests.
Every fixed bug must add a fast reproduction at that level. The DinD image
cache and the reduced timeouts stay reserved for the single E2E journey;
`E2E_FRESH=1` still allows starting from scratch.

## Completed spec amendments

Twelve inconsistencies found between the artifacts during implementation, fixed at the source:

1. ADR-018/ADR-022 files not renamed (broken links from the index)
2. OpenAPI at 3.1 while oapi-codegen (ADR-025) only supports 3.0 → converted
3. `teams.personal` exposed by the OpenAPI, absent from the data dictionary
4. Instance SSH key vs `private_keys.team_id NOT NULL` → `is_instance` + CHECK
5. `jobs.steps`/`result`/`retry_of_id` exposed by the OpenAPI, absent from the dictionary
6. `deployments.error_message` likewise
7. `deployment-engine` prescribed `AkerDock/<uuid>` images — Docker refuses uppercase
8. No endpoint for persistent volumes while `delete_volumes` existed → endpoints added
9. ADR-024 requires SSE for statuses but no events endpoint → `GET /events` added
10. The contract placed the S3 Storages CRUD "out of v1, provisioned via the UI" while backup plans require an `s3_storage_uuid` and the UI does not exist → 5 `/s3-storages` operations added
11. Notifications were "out of v1" while ADR-019 requires them and nothing allowed configuring them → 7 `/notification-channels` operations added; `notification_deliveries` table added to the dictionary (debounce and idempotency are derivable from neither of the two planned tables)
12. Signed Git webhooks were specified (`git-webhook-protocols.md`, INV-009) but no endpoint allowed creating the receiving endpoint → `POST/DELETE /applications/{uuid}/webhook-endpoint` added (the secret is returned only once)

Amendments no. 13 through no. 29, made along the batches, are documented where they were
settled (above) rather than restated here. The most recent ones:

24. The terminal was "out of v1" **entirely**, on the grounds that a WebSocket cannot be described in OpenAPI 3.0. But only the *stream* is indescribable: the **session opening**, for its part, is an ordinary REST operation — and leaving it out of the contract would have taken it out of the RBAC matrix generated from `x-required-permission` (hence never tested) and made it non-scriptable, contradicting §25.2 ("any capability visible in the UI is scriptable"). → 3 operations `POST .../terminal-sessions` added (application, database, server); the WebSocket stays out of the contract, like `/auth`. The dictionary's `terminal_sessions` table gained `token_hash`/`token_expires_at`/`claimed_at`: the attach token's single use was derivable from no planned column

25. Adoption (§20.7) was specified but **no endpoint** carried it — the "inbound migration path" (ADR-023) was reachable neither from the UI nor from a script, contradicting §25.2. → 6 operations added: `POST/GET /servers/{uuid}/adoption-scans`, `GET /adoption-scans/{uuid}`, `POST /adoption-scans/{uuid}/adopt`, `POST /applications/{uuid}/disown`, `POST /services/{uuid}/disown`. The dictionary gains `adoption_scans` (§6.8), `resources.adopted_at`/`adoption` and `persistent_storages.external_name`: "which container serves this resource before normalization" and "which volume keeps its original name" were derivable from no planned column

26. Internal database backups (compose-spec §10) had the schema (`service_component_id` FK, three-target CHECK) but **no operation**: a component classified as a database was reachable by nothing. → 10 operations `/service-components/{uuid}/backups[...]`, exact mirror of the database operations; `BackupPlan.database_uuid` stops being `required` (it is null for a component plan). Contract bug found along the way: the restores promised a mandatory `confirm=true` and no handler checked it — the body is now required everywhere (`422` otherwise)

27. Cleanup (§3.7) had its columns (`servers.cleanup_*`, since migration 00006) but **nothing exposed or read them**: the capability was configured nowhere and executed never. → `cleanup_*` fields added to `Server`/`ServerUpdate`, `POST /servers/{uuid}/cleanup` added, scheduling columns `cleanup_next_run_at`/`cleanup_last_run_at` added (migration 00043) — the cron window was derivable from no planned column

28. Uptime monitoring (ADR-017) had neither table nor operation, and PRD §13 still carried the pre-ADR wording ("no built-in uptime monitoring") — corrected to say what the ADR decides (rewording is not deciding). → 6 operations `/uptime-checks[...]`, `uptime_checks`/`uptime_check_results` tables (§6.9/§6.10, migration 00044), `uptime_check_kind`/`uptime_status` enums

29. Shared variables (§5.4) were in the dictionary (§8.6) but neither migrated nor exposed — the PRD's `{{team.VAR}}` syntax was resolvable nowhere, and compose-spec §3.2 promised "shared scopes merged by the caller" that no caller merged. → 4 operations `/shared-variables[...]`, migration 00045 conforming to the dictionary, resolution wired into the runtime env, the build env and the compose stacks

31. GitLab/Gitea feedback parity (§20.4.6) required an API token "stored encrypted on the git source" (protocols §4.1/§6.1) and three of the four §20.4.7 trigger controls had their columns (`preview_require_label`, `preview_comment_commands_enabled`, `preview_cancel_obsolete_builds`, migration 00007) but **nothing exposed or read them** — configurable nowhere, applied never. → fields added to `Application`/`ApplicationUpdate`: the three controls, plus `git_api_token` (write-only, never read back — INV-003) and `git_api_url` (self-hosted), reflected by `git_api_token_set`. The dictionary gains `git_sources.api_token_enc` and `previews.repo_reference` (migration 00048): "where the feedback phones home" was derivable from no column — the GitHub App path goes through the `repositories` cache, the manual webhooks only have the delivery
